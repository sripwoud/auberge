# ADR-0018: Shell completion is static, generated at runtime by a `completions` subcommand

## Status

Accepted, 2026-08-11.

## Context

The CLI has 12 top-level subcommands, most with nested subcommands, aliases (`dp`, `hs`, `ss`, …), global flags, and `value_enum` arguments. None of this is tab-completable; discovery happens through `--help`.

clap 4 with the derive API makes completion nearly free via `clap_complete`, but three design questions needed answers:

1. **Static or dynamic?** Static completion covers compile-time truth: subcommands, flags, aliases, `ValueEnum` values. Dynamic completion (clap_complete's `unstable-dynamic` feature) additionally completes runtime values — App names for `deploy`, Host names for `-H`, Key Registry keys for `config set` — but requires per-arg completer functions on an API that is explicitly unstable across minor versions, plus a different shell-registration mechanism (`COMPLETE=<shell> auberge`).
2. **How do users obtain the script?** A `completions <shell>` subcommand printing to stdout, or pre-generated files shipped as GitHub release assets.
3. **Which install pattern do the docs recommend?** Eval on every shell start (`source <(auberge completions bash)`) or a one-time file drop into the shell's lazy-loaded completion directory.

## Decision

- **Static-only.** No `unstable-dynamic`, no per-arg completers.
- **Runtime generation via a visible `auberge completions <shell>` subcommand.** All shells `clap_complete::Shell` offers (bash, zsh, fish, elvish, powershell) come free because `Shell` is itself a `ValueEnum`.
- **Docs recommend eval-in-rc as the primary install pattern** (`source <(auberge completions bash)` in `~/.bashrc`), with the file-drop variant noted as an alternative for shell-startup-time purists.

## Consequences

**Positive:**

- One small dependency (`clap_complete`), ~20 lines of code, zero unstable APIs.
- The script can never drift from the installed binary: it is generated by that binary at shell start. This matters because the mise-installed binary routinely lags master, and new subcommands land often (`versions`, `bichon` both shipped within months).
- Aliases and `--output {human,json}` enum values complete out of the box.

**Negative:**

- `auberge deploy <TAB>` will not suggest App names, `-H <TAB>` will not suggest Hosts. Mitigated: the interactive skim picker already covers this — omitting the value (`select_or_arg`) prompts with fuzzy search, which handles "I don't remember the name" better than tab completion does.
- Eval-in-rc costs one binary invocation per shell start (~10 ms) and errors if the rc line runs before mise puts `auberge` on `PATH`.

## Alternatives considered

- **Dynamic completion** (`unstable-dynamic` + `ArgValueCompleter` for Hosts, Apps, Key Registry keys). Rejected: the skim-based `select` flow is already the runtime-value UX; dynamic completion would be a second, parallel channel to the same data, bought with an unstable API and per-arg completer maintenance.
- **Pre-generated scripts shipped as release assets.** Rejected: both distribution channels (mise github backend, `cargo install`) deliver only the binary — nothing installs sidecar files, so users would fetch the script manually and it could drift from the binary version they actually run.
- **File-drop as the documented default** (`auberge completions bash > ~/.local/share/bash-completion/completions/auberge`; zero startup cost, lazy-loaded on first TAB). Rejected as primary: it goes stale on every upgrade until manually re-run, and nothing in the mise upgrade flow reminds anyone. A completion script that silently doesn't know a just-shipped subcommand is worse than 10 ms per shell. Documented as the alternative.
